# ClipForge

**The All-in-One GIF & Video Studio** — a Windows desktop tool for turning long videos
into trimmed GIFs and size-targeted video clips.

Built with Electron + React + TypeScript, with the interface built from shadcn/ui
components styled by Tailwind CSS. The media work is done by three bundled
command-line tools: FFmpeg, yt-dlp, and gifski.

## What it does

- **URL → GIF or video.** Paste a YouTube, X, TikTok or direct video URL and ClipForge
  resolves its metadata with `yt-dlp`, downloads the media once, and works on the local
  file from then on. The download is deliberate rather than piped straight into FFmpeg:
  an MP4 whose `moov` atom sits at the end - what most servers send - cannot be read from
  a pipe at all, and trimming, cropping and the filmstrip all need an input FFmpeg can
  seek in. The downloaded copy is reused by the export and removed when the app quits.
  A post the site serves only to a signed-in visitor is fetched with a saved session —
  see [Links that need a signed-in session](#links-that-need-a-signed-in-session).
- **Local files.** Drag a video or GIF anywhere into the window. MP4/M4V/WebM stream
  directly to the preview; other containers (MKV, MOV, AVI, TS) are losslessly remuxed
  to a temporary MP4 first, so the preview always seeks correctly.
- **Real trim timeline.** A thumbnail filmstrip generated by FFmpeg, draggable start and
  end handles, and timestamp fields that accept `HH:MM:SS.mmm` or plain seconds.
- **Watermark removal.** Mark up to four areas over the preview — the corner presets drop
  a logo-sized box in one click — and FFmpeg's `delogo` rebuilds each one from the
  pixels immediately around it, in every output format. The boxes are source pixels and
  are applied before the crop and the resize, so cropping and a logo removal compose.
  A box is always held one pixel inside the frame: `delogo` samples a ring around itself
  and aborts the whole export with *Logo area is outside of the frame* if it cannot,
  which is exactly where a watermark tends to sit. It is an interpolation filter, so a
  mark over a busy, moving background is replaced by a soft blend rather than
  reconstructed — draw the box a few pixels wider than the mark, and prefer a crop when
  the mark sits on the frame edge with nothing around it.
- **Two GIF engines.** `gifski` (cross-frame dithering, highest quality) and
  `FFmpeg palette` (palettegen/paletteuse, fastest). gifski runs as FFmpeg PNG frame
  extraction followed by gifski assembly, and its scratch frames are always removed.
- **Video toolbox.** Trim with libx264, keep or strip the audio track, and compress to a
  target size (10 MB, 25 MB) by computing the bitrate budget for the clip length.
- **Hardware aware.** Reads CPU cores, RAM, and the FFmpeg hardware encoders
  (NVENC / Quick Sync / AMF) available on the machine and recommends settings.
- **Self-healing tools.** If a media tool is missing, a card opens in the workspace and
  downloads the official build with per-tool phases (looking up → downloading →
  extracting → installing → verifying), live byte counts, speed, ETA and a cancel
  button. Downloads resume from a partial file instead of restarting a 111 MB fetch.
- **English and 繁體中文.** Every UI string lives in a typed dictionary and switches
  instantly from Settings; a parity test fails the build if a key is missing.
- **Tabbed inspector.** The right column switches between the Export controls and an
  Output box that loops the finished GIF or video next to the settings and file size
  that produced it, with open-folder, copy-image and copy-path actions. A finished
  export flips to that tab on its own.
- **Fullscreen preview.** The fullscreen button puts the preview on the whole screen with
  the transport controls, so a loop or crop can be judged at full size; `F11` toggles
  the whole window instead. Both are plain HTML5 fullscreen and video, not a plugin.
- **Editor-style shortcuts.** Space plays, `←`/`→` step single frames, `I`/`O` set the
  in and out points at the playhead, and the preview can loop the selection so a GIF can
  be judged before it is encoded.
- **Updates itself.** An installed copy checks its GitHub release feed shortly after
  startup, downloads a newer build in the background and offers a restart — with the
  version and status always visible under Settings → *Hardware & about*.
- **Frameless window.** No OS title bar: the app draws its own traffic-light-free
  controls in the top corner, and the sidebar, top bar and settings header double as
  drag regions. Window minimum is 900×560, and the whole interface scales down with the
  window so a 1536×816 work area (a 1080p laptop at 125%) shows everything without
  sideways scrolling.

## Requirements

- Windows 10 / 11 (x64)
- Node.js 20 or newer (developed against Node 26)
- The bundled binaries. `npm run prepare:binaries` downloads them, or the app can install
  them at runtime from the Settings page.

## Development

```powershell
npm install
npm run prepare:binaries   # downloads ffmpeg, ffprobe, yt-dlp, gifski into resources/bin
npm run dev                # Vite dev server + Electron
```

Other useful scripts:

```powershell
npm run typecheck     # TypeScript for both the main process and the renderer
npm test              # unit tests for argument builders, install planning and i18n
npm run build         # compile main process (tsc) and renderer (vite)
npm run release       # package and publish a GitHub release (see Releasing)
```

To exercise the production path without packaging, run the built renderer directly:

```powershell
set CLIPFORGE_DEV=0
npx electron .
```

## Building the installer

```powershell
npm run dist
```

This runs `prepare:binaries`, builds both targets, and produces
`release/ClipForge-Setup-0.1.0.exe`. The NSIS installer bundles `resources/bin` as
`extraResources`, so an installed copy of ClipForge needs no additional downloads.

If the binaries are already in `resources/bin`, `prepare:binaries` skips them and the
build works offline.

## Releasing, and how installed copies update themselves

`release.bat` commits, pushes, builds the installer and publishes it as a GitHub
release. Installed copies then find the new version on their own.

```powershell
release.bat                     # full run against the configured origin remote
release.bat check               # preflight only: repo, version, token, nothing else
```

| Switch | What it does |
| --- | --- |
| `REPO=owner/name` | repository to create or attach and release to |
| `VERSION=1.2.3` | sets `package.json` before committing; the tag follows it |
| `PUBLIC=1` | create a missing repository as public instead of private |
| `SKIP_CHECKS=1` | skip typecheck and unit tests |
| `SKIP_BINARIES=1` | keep the existing `resources/bin` payload |
| `NO_TAG=1` | commit and push without tagging a release |
| `COMMIT_MSG="..."` | override the generated commit message |

A GitHub token is required to publish: either `GH_TOKEN` in the environment, or
`gh auth login` once and the script reuses `gh auth token`.

Releases are published to [`alex200376/clipforge`](https://github.com/alex200376/clipforge/releases),
which is the repository the packaged `resources/app-update.yml` points at. On a folder
with no `origin` remote yet, pass `REPO=owner/name` and the script creates the
repository with the GitHub CLI when available (private unless `PUBLIC=1`), falling back
to a plain remote when `gh` is missing or the repository already exists.

How the pieces fit together:

- **The token stays in the shell.** electron-builder reads `GH_TOKEN` from the
  environment; nothing is written to a file.
- **`--publish always` runs with `-c.publish.releaseType=release`.** GitHub releases
  default to *draft*, and a draft release is invisible to the updater, so a release
  that nobody can update from would look like success.
- **electron-builder writes two files that matter.** `release/latest.yml` is the feed
  (version, size, sha512), and `resources/app-update.yml` inside the packaged app is
  what the running app reads. Both come from the same build, so the version a client
  sees can never disagree with the installer it downloads.
- **The in-app side lives in `src/main/updates.ts`.** It checks ~5 s after startup
  (settings → *Check for updates on startup*), downloads in the background, and offers
  a restart. The failures electron-updater produces are whole HTTP responses, so
  `src/shared/updates.ts` condenses them into one sentence before anything shows them.
- **Only an installed copy can update itself.** A run from source has no
  `app-update.yml`, so the app reports *Unavailable in this run* instead of failing an
  invisible request.
- **An update is never silent.** Settings → *Hardware & about* carries the version and
  the status; a ready update also raises a card in the workspace and a line in the
  activity log.

## App icon

The icon is generated from `assets/icon-source.png` — no image tooling required, since
`scripts/make-icon.mjs` decodes the PNG, trims it to the artwork's bounding box,
re-centres it and resamples it down to every size Windows asks for:

```powershell
npm run make:icon                            # ico + png + the in-app brand mark
node scripts/make-icon.mjs --preview p.png   # contact sheet for judging small sizes
```

| Output | Used by |
| --- | --- |
| `build/icon.ico` (16 → 256) | the exe, the installer and the taskbar |
| `build/icon.png` (512) | ships as an extra resource, so the runtime window icon matches |
| `src/renderer/assets/brand.png` (128) | the sidebar brand mark, imported by the UI |

All three are committed, because electron-builder and the renderer build read them at
package time. They are generated from one source rather than bundled by hand, so the
shell icon and the in-app logo cannot drift apart. Replace `assets/icon-source.png` and
re-run the script to change the branding; nothing else refers to a fixed image.

## Installing the media tools

`src/shared/installPlan.ts` is the single source of truth for where each tool comes from
and which binaries a download provides. Two details matter:

- **ffprobe never downloads on its own.** It ships inside the FFmpeg archive, so the
  FFmpeg spec stages `ffmpeg.exe` and `ffprobe.exe` together and a request for either
  name produces exactly one download.
- **gifski's Windows build is not on GitHub.** Releases after 1.32.0 only carry source
  and Linux packages, so the version is resolved from the GitHub API and the zip is
  fetched from `gif.ski` — the same scheme the Scoop manifest uses.

Every install is verified by running the tool's version command, which catches an
antivirus quarantine or a truncated download that would otherwise look successful.
The same catalog drives `scripts/prepare-binaries.mjs` at packaging time.

## Links that need a signed-in session

Some sites serve a post only to a visitor who is signed in. X is the common case: asked
without a session it answers with a `TweetTombstone` instead of the post, `yt-dlp` reports
that the tweet has no video, and the link reads like a broken one. Settings → Media tools
has a **Sign in** button for this. It opens the site's own sign-in page in a window of its
own; the password is typed there and never reaches ClipForge, and what is kept is the
session cookie file (`yt-cookies.txt` in the app's data folder, removable with **Sign out**)
that `--cookies` hands to `yt-dlp` on every later import.

Three details are deliberate:

- **`--cookies-from-browser` is not used.** Measured on Chrome and Edge 153: both fail
  with `Failed to decrypt with DPAPI`, because the cookie database is now encrypted with a
  key only the browser can unwrap. Reading the cookies out of a window Chromium already
owns avoids that, and needs no extension.
- **The cookies are filtered by domain** before they are written, so a sign-in that went
  through Google or Apple cannot put a third party's session into a file that later
  downloads are fetched with.
- **A refusal is diagnosed, not guessed.** "No video could be found in this tweet" is what
  `yt-dlp` says both for a post that needs a session and for a link that is dead, so the
  app asks X's public syndication endpoint which one it is - a tombstone means signing in
  will help, a 404 means the post is gone - and reports the one that is true.

## Error codes and translation

Main-process failures carry a stable code (`missing-gifski`, `verify-failed`, …) inside
the message so it survives Electron's error serialization. The renderer maps those codes
to translated sentences and falls back to the raw technical message when it has no entry.

## How local media reaches the UI

The renderer never receives filesystem paths it can read. The main process registers a
`clipforge://` scheme and hands out short-lived tokens; the protocol handler resolves a
token back to a file and streams it with range support so `<video>` can seek.
